# 首版链路验收规范（M00.1 批次交付）

状态：本批不存在运行时。**尚未执行任何产品功能测试**：没有实现、没有 API、没有 UI、没有模型接入，`reports/BATCH-001.md` 与三张卡的报告都记 `integration_evidence_kind=not_run`。
本规范不是测试框架，也不新建代码工程：它是给独立验收者的人工核对清单，逐条说明输入、操作、可观察期望、判失败条件、样本引用与所覆盖的 FLOW-A / 卡验收 ID。样本哈希以 `reports/evidence/M00.1.02/artifact-manifest.json` 与 `reports/evidence/M00.1.03/artifact-manifest.json` 为准，本文件不记录自己的哈希以免循环引用。

规则来源：`docs/product/first-flow.md`（修订 r2，含 D1–D5 裁定结论）第 4.1 节字段集、第 6 节缺失信息、计算与来源规则。

## 0. 验收方式与前提

1. 验收者按本文档逐场景打开引用的样本 JSON，与样本内嵌的 CSV 原文及期望逐字段比对。
2. 金额一律是十进制字符串；复算用标准库 decimal（`Decimal(qty) * Decimal(unit_price)`），不用浮点。
3. 期望里出现 `null` 的地方就是未知，不允许被 0 或猜测值替代；`未提及` 不是 `null`，`不适用` 也不是 `null`。
4. 本批没有实现，因此场景 V1–V4 核对的是样本与期望本身的正确性与可核对性；V5–V7 是给后续实现的验收场景，本批只固定它们的行为口径，不产生运行证据。
5. 预留输入 V8 的期望由验收者生成，不由开发者提供。

## 2. 场景

### V1 首次执行·正常（ff-normal-01）

- 输入：需求文本（青湾会展服务，10 月 12–14 日，滨江市国际会展中心，3 天同声传译、2 套耳返设备、50 个会议资料袋，且写明“单价都是含税价”）+ 3 行 CSV（`qingwan-event-price-list.csv`：3×1800.00、2×120.50、50×2.40，币种列 USD）。
- 操作：用户提供文本与 CSV（U1）→ 查看成果卡（U2）。
- 可观察期望：需求摘要与四类需求要素齐备；三行明细的行小计为 `5400.00`、`241.00`、`120.00`；合计为 `5761.00` USD 且 `complete_total` 有公式与操作数引用；`partial_subtotal` 为 `不适用`（全部行可计算）；币种 `USD` 与含税口径 `含税` 均标 `输入`；待确认问题清单为空。
- 判失败条件：合计不是 5761.00 或与小计之和不符；把币种改成非 CSV 写明的值；出现任何“待确认”问题；任一金额用浮点表示或出现 0.00 之外的静默默认值；含税口径被当作地域默认值而没有输入来源。
- 对应：FLOW-A01、FLOW-A06；卡验收 M00.1.02-A03。

### V2 首次执行·缺失（ff-missing-01）

- 输入：需求文本（北海文旅，10 月 8–9 日，北海滨海剧场，现场技术支持 2 天、物料运输 1 车次、加急排期费“按 180.00 算”、附赠 20 本展会手册）+ 4 行 CSV（`beihai-roadshow-price-list.csv`：950.00 USD、空单价 EUR、150.00 USD、0.00 USD）。
- 操作：同 V1。
- 可观察期望：第 1 行小计 `1900.00` USD；第 2 行 `unit_price` 与 `subtotal` 为 `null`（空单元格）并有关联问题 Q1；第 3 行 `unit_price` 为 `null` 且同时记录两个候选（150.00 来自 CSV、180.00 来自需求文本），不选其中任何一个，问题 Q2；第 4 行小计 `0.00`（已知的零）；`partial_subtotal` 为 `1900.00` USD 并明确标注为部分小计；`complete_total` 为 `null`（行未定且混币种）；含税口径为 `null` 与问题 Q3；`null_and_zero.null_values` 的 6 个路径与实际 null 一致。
- 判失败条件：任何缺失值被填成 0、被从其他行或其他文档推算、或从两个冲突候选中静默选取一个；部分小计冒充完整合计；`0.00` 与 `null` 混为一谈；把 EUR 行按客户所在地改成 USD，或把 USD 与 EUR 相加成单一总额。
- 对应：FLOW-A03、FLOW-A06；卡验收 M00.1.02-A02。

### V3 用户纠正（ff-correction-01，同一业务任务）

- 输入：V2 的任务处于 `waiting_user`，用户给出 C1（物料运输按 320.00 一车次，一次性）、C2（加急排期费按清单 150.00，一次性）、C3（单位写成“天”，格式纠正）、C4（清单单价按含税看，确认成规则）、C5（币种一律取清单列，确认成规则）。
- 操作：用户在 S2 补充/纠正输入（U3）→ 查看纠正后的成果卡 → 看到 S3 保存提议（U4 之前）。
- 可观察期望：任务身份不变（同一 task_id 与业务幂等键，不新建任务、不新建 attempt），旧结果不被覆盖；纠正后行小计为 `1900.00` USD、`320.00` EUR、`150.00` USD、`0.00` USD；按币种合计 `2050.00` USD 与 `320.00` EUR，两条合计都带公式与指向本次明细小计的操作数；`complete_total` 为 `null` 且原因为混合币种（`不适用`），不做换汇；纠正后结果是**完整快照**（含需求摘要、四类需求要素、完整明细与缺失/问题清单），并显式写明继承哪份基线期望、哪些字段继承未变，继承字段与基线逐项相等；被改字段标 `用户确认` 且 `changed_fields` 能追溯到 C1–C4；C3 不触发任何重算（`affects_amount=false`）；待确认问题清零，运行时身份占位（如包哈希）不得混成用户业务缺失项；保存提议里固化的规则只有 RULE-CUR 与 RULE-TAX，提议不含上次的客户资料与具体金额。
- 判失败条件：把纠正当成新任务或新 attempt；纠正后仍显示旧值、或旧结果被就地覆盖而无从追溯；纠正后结果只给差分、无法当完整快照逐字段核对，或没有写明继承来源；继承字段与基线不一致；把包哈希这类运行时占位写成用户待确认问题；被改字段没有标 `用户确认`；把 320.00 / 150.00 这类一次性取值写进规则；把 C2 的“这次选 150.00”固化成“以后冲突都取清单价”；把 C3 的单位格式当成价格变更触发重算；接受提议即把功能置为已启用。
- 对应：FLOW-A04、FLOW-A05、FLOW-A03；卡验收 M00.1.02-A03、M00.1.01-A01。

### V4 再次使用·规则迁移（ff-reuse-01，新业务任务）

- 输入：新的需求文本（云汀路演团队，11 月 3–4 日，合肥市文化馆，现场支持 2 天、物料运输 1 车次，文本说“这次要给欧洲客户看，按不含税口径报给我”）+ 新 CSV（`yunting-price-list.csv`：2×1050.00 GBP、1×165.00 EUR），固定使用已发布的技能 v1。
- 操作：用户提供新文本与新 CSV（U5），不重新讲规则。
- 可观察期望：这是新任务（样本标记 TASK-REUSE-01、新业务幂等键 IDEM-REUSE-01、初始 attempt 1），不是上一次任务的延续；币种严格取 CSV 列（第 1 行 `GBP`、第 2 行 `EUR`），不因“欧洲客户”改成 EUR，也不按客户所在地推断，顶层币种给出 `source_ref` 指向本次 CSV 的 currency 列；行小计 `2100.00` GBP 与 `165.00` EUR；按币种分别列出（两条合计都带公式与操作数）且不合成单一总额；结果是与首次执行相同的 13 个业务字段构成的完整快照（混币种时另带按币种合计 `currency_totals`，不新增其他字段名）；每条金额都能回溯到本次输入（小计的操作数是本次 CSV 单元格，币种合计的操作数是本次明细行小计）；含税口径因本次显式要求（不含税）与已保存规则 RULE-TAX（含税）冲突而为 `null` 与一个待确认问题，不静默覆盖输入；结果结构与首次使用一致，用户无需重新教学。
- 判失败条件：沿用旧的 task_id / 幂等键，或把新输入塞进旧任务的 attempt；币种取自推断而不是 CSV 列，或顶层币种没有来源；任一金额没有公式/操作数、或小计与合计无法用本次输入复算出来；结果字段集与首次执行不一致（第二套 Schema）；两币种相加成单一总额或做换汇；把输入的“不含税”静默改成规则里的“含税”（或反之）；结果里出现上一次的客户名、联系人、地点或金额。
- 对应：FLOW-A07、FLOW-A03、FLOW-A06；卡验收 M00.1.03-A02、M00.1.01-A01。

### V5 拒绝保存（行为场景）

- 前提：S3 已给出保存提议（附规则摘要与适用范围）。
- 操作：用户拒绝提议。
- 可观察期望：不产生任何可复用功能（不出现候选包、不出现 active 指针变更）；本次工作结果与纠正记录保留可查；S5 不会用到被拒绝的功能。
- 判失败条件：拒绝后仍生成候选包或启用版本；本次结果被删除；后续以“已被保存”为前提自动复用。
- 对应：FLOW-A05、FLOW-A08；卡验收 M00.1.01-A01。

### V6 保存后验证失败或缺授权（行为场景）

- 前提：用户接受提议（只授权制作候选包）。
- 操作：候选包按 draft → testing → ready 走完（或中途失败）；缺少覆盖该版本的授权时不自动启用。
- 可观察期望：验收通过、包哈希与拟发布版本一致、且授权覆盖该版本与所需权限，才切换 active；验证失败或缺授权时显示候选状态与失败原因，用户可修改或取消；此期间 S5 不把候选当作已启用功能。
- 判失败条件：接受提议后直接生效（跳过 draft/testing/ready 或跳过独立验证）；失败被隐藏成成功；缺授权时静默启用或静默上传到云端。
- 对应：FLOW-A05；卡验收 M00.1.01-A02、M00.1.03-A01。

### V7 停用（行为场景）

- 前提：某版本已 active，并可能正在服务一个已提交的运行。
- 操作：用户停用该版本（U6）。
- 可观察期望：后续自动选用被阻止；历史结果与规则来源保留；已提交的运行按 C03 的取消语义单独处理，不等价于被停用顺带取消。
- 判失败条件：停用删除历史结果或来源记录；停用被当作取消正在执行的任务；停用后新输入仍然自动选用该版本。
- 对应：FLOW-A08；卡验收 M00.1.01-A01。

### V8 预留输入（ff-holdout-01，期望由验收者生成）

- 输入：`tests/fixtures/first-flow/holdout.json`（只含需求文本与内嵌 CSV，不含任何预期结果）。
- 操作：由独立验收者在本批提交后，按 `docs/product/first-flow.md` 生成该输入的期望并使用；本批不生成、不记录、不在日志或报告中描述其期望值。
- 可观察期望：本文件与公开样本的取值与缺失组合不同；它不是代码生成示例、演示样例或测试替身。
- 判失败条件：任何公开文件（含本文件、报告、日志、期望文件）写出该输入的期望结果；或把它当实现样例交给开发者；或声称开发者对该输入真正未见。
- 对应：FLOW-A03、FLOW-A06；卡验收 M00.1.03-A01。

### V9 输入不完整（行为场景）

- 前提：用户只给了需求文本或只给了 CSV。
- 操作：提交任务。
- 可观察期望：链路不启动，返回 C01 的 `INVALID_INPUT`，不产出任何推测性结果，也不退化成“仅文本”的另一条链路。
- 判失败条件：缺一半输入仍产出结果；出现第二条入口或替代变体。
- 对应：FLOW-A01；卡验收 M00.1.01-A01。
