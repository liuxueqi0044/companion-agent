# 运行底座决策：Hermes 与 Codex

日期：2026-09-23。结论是当前工程主选方案；性能与集成质量须通过 M00 验证。

## 决策

**采用一主一辅：Hermes 负责用户长期状态、日常协作、主动任务与工作习惯学习；Codex 专门负责脚本、工具和小功能的实现、修改、测试。** 主控使用足够强的模型，常规子任务使用便宜模型。

Codex 是主选工程执行组件，不能把它理解为“只会写代码”。它也支持工具调用、持续会话、审批和应用集成。选择 Hermes 作为外层骨架，是为了复用与本产品直接有关的长期功能，不是认定 Codex 比 Hermes 笨。

模型决定推理与生成能力的一部分；框架还会影响上下文组织、工具使用、持续执行、权限、恢复和用户体验。没有同模型、同工具、同数据的对照测试，不能从两份 README 得出谁在我们的产品上更强。

## 三种方案

| 方案 | 可复用部分 | 我们要补的部分 | 本项目结论 |
| --- | --- | --- | --- |
| Codex 单底座 | App Server、工具循环、文件与代码执行、会话恢复、MCP、Skills、子 Agent 和模型配置 | 面向个人伙伴的记忆管理体验、通知策略、用户工作习惯学习与产品服务 | 可行；保留为主底座替代方案 |
| Hermes 单底座 | 长期记忆、技能学习、模型接入、委派、目标、定时任务、消息渠道 | 品牌前端、多用户服务、技能发布体验与成本控制 | 最快覆盖产品需求；工程任务表现仍需测试 |
| Hermes 主控 + Codex 工程工作者 | 复用前两者相应能力，用有边界的工程任务连接 | 跨运行时任务交接、隔离、成果与费用合并 | **主选；若收益不覆盖集成成本则退回单底座** |

Codex 的开源范围是 CLI、App Server、SDK 等执行框架与接口；模型访问和托管产品另行提供。不能把 ChatGPT 订阅、桌面界面及所有连接器视为可随代码重新分发的免费组件。[官方开源说明](https://learn.chatgpt.com/docs/open-source)、[平台集成说明](https://developers.openai.com/blog/codex-as-a-platform)

## 已核实的关键接口

Codex 官方 App Server 提供线程/回合控制、流式事件、工具审批等应用集成接口。优先使用同一受控执行环境中的 stdio；远程 WebSocket 和动态工具字段有实验性限制，不让首版依赖它们。跨云边界通过我们自己的认证 API，沙箱内部使用 stdio。[App Server 文档](https://learn.chatgpt.com/docs/app-server)

Codex 配置已包含子 Agent 默认模型和记忆生成等设置。因此“Codex 没有多 Agent/记忆”不是本次选型依据。不同提供商、模型协议与功能兼容性逐项测试；配置项存在不代表所有模型都能等价运行。[配置参考](https://learn.chatgpt.com/docs/config-file/config-reference)

Hermes 提供 Runs、Sessions、Jobs 等 HTTP 接口，可以用于我们的界面；普通聊天兼容端点不承担全部任务生命周期。普通 `delegate_task` 的子模型由配置统一指定，任意按子任务换模型不能当成已有能力。需要不同配置的持久工作者时再选其 Kanban 机制。[API](https://hermes-agent.nousresearch.com/docs/user-guide/features/api-server)、[委派](https://hermes-agent.nousresearch.com/docs/user-guide/features/delegation)、[Kanban](https://hermes-agent.nousresearch.com/docs/user-guide/features/kanban)

## 一个可以直接复用的组合入口

Hermes 已有可选的 Codex App Server runtime：它把某个运行配置下的工具循环交给 Codex，外层仍保留 Hermes 的部分会话与学习功能。当前文档标注 beta，且列出 `delegate_task`、`memory`、`session_search` 等工具在该路径不可用；cron 也注明未专门测试。**因此不在用户主配置上全局打开；先只用于工程工作者配置。** [现有接入及限制](https://hermes-agent.nousresearch.com/docs/user-guide/features/codex-app-server-runtime)

这条接入只替换工作者内部的执行循环，不等于获得两个模型同时控制同一任务。不要把“支持接入”写成“已经适配我们的云沙箱、租户隔离与全部工具”。

## 实际运行方式

1. 用户始终只面对一个伙伴。主会话和用户记忆由 Hermes 持有。
2. 主控发现需要开发工具时，产生 `EngineeringTask`：目标、允许访问的输入、复用候选、输出约定、验证要求、预算。
3. 产品工具适配器启动隔离的工程工作者。优先在隔离环境内复用 Hermes 已有 Codex runtime；工作者只收到任务所需上下文。
4. Codex 实现并运行检查，返回 `EngineeringResult`、成果文件、测试证据、实际费用信息与未解决项。
5. 主控判断结果是否满足用户需求。可机械验证的条件必须查实际结果，不仅阅读工作者的自我评价。
6. 通过后进入技能候选版本。产品发布器切换生效版本，再呈现给用户。

工作者不保存另一份用户人格与长期记忆，不自行增加主动通知，不重新调用主控形成循环。初始并行上限为 2、委派深度为 1；这些是可调工程初值。

## 集成路径与退出条件

用户已有 Agent 是同等重要的执行路径：工程接口可以选择用户本机 Codex，也可以选择 Claude Code。Codex 是默认工程执行器，不是只允许接这一家的产品限制。本机官方登录、订阅边界、离线恢复和主控自身费用见[外部 Agent 联动](06-agent-connections.md)。下文 A/B 指云端工程环境的集成选择；用户本机路径直接连接官方程序，无须额外安装一套 Hermes 工程工作者。

**路径 A，优先验证：** 在隔离工程环境内运行最小 Hermes 工程配置 + 其原生 Codex runtime，复用现有事件桥与审批桥。模型凭证通过受控服务注入；不迁移开发者自己的 Codex 配置或账号插件。

**路径 B，只有 A 不适合云隔离时才采用：** 在同一 `EngineeringWorker` 接口后面直接使用官方 Codex SDK/本地 App Server，编写小型任务与成果转换层。它代替 A，不与 A 重叠运行。SDK 适合范围明确的编程任务；需要交互审批时使用 App Server。[Codex SDK](https://learn.chatgpt.com/docs/codex-sdk)

**退出组合方案：** 若两条路径都需要持续修改上游核心循环，或工程任务成功率/用户等待/费用没有可重复收益，则先使用 Hermes 单底座。若后续主价值集中在复杂工程工作、且 Hermes 周边被证明大多用不到，则改为 Codex 主底座，并通过现有产品接口保留 UI、账户、工具和技能资产。

## 第一轮对照测试

使用相同资料、相同工具权限、同档预算；能够使用相同模型时先做同模型对照，另做各框架推荐配置测试。两组结果分开记录，避免混淆模型与框架收益。

| 测试 | 合格证据 |
| --- | --- |
| 表格整理与回复草稿 | 字段正确、成果可打开、缺失信息未被编造 |
| 根据两次用户纠正开发转换脚本 | 复用已有库；旧样本与未见样本均通过；结果可重复 |
| 长任务中途断开客户端 | 云端任务继续；重新连接后可查询真实状态 |
| 执行进程被终止 | 状态明确为中断；已完成成果可找回；有副作用的动作不盲目重试 |
| 新技能出现错误 | 可定位失败版本并回退；旧技能仍能使用 |
| 工程工作者撤销/超时 | 真实执行停止或明确显示仍在停止；不伪报取消成功 |

同时记录成功率、人工介入次数、总费用、延迟、集成代码和运维负担。本轮文档没有执行以上测试，不给出虚构的胜率或性能排名。
