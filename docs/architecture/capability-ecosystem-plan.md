# Morrow 能力生态与跨 Agent 插件适配提案

日期：2026-09-27。状态：原设计提案的首期限定范围已由 CORE-021 实现；当前实现与未覆盖项以
`docs/development/CORE-021.md`、`docs/product/CAPABILITIES.md` 和 `reports/core-021/README.md` 为准。
根据用户提出的跨生态复用、按用途选择、自由搭配形成。补充现有产品架构；不替换当前交接，不改变历史验收与邀请包完成范围。

## 1. 产品目标

用户按自己想完成的事情添加能力，例如整理资料、制作内容或安排日常。产品处理来源差异、依赖、配置与调用。用户可以自己选择，也可以让 AI 推荐和搭配。

主界面仍以当前个人空间为中心。“添加能力”作为轻量入口；能力增加不等于主界面增加一排按钮。完整界面包继续自由替换，能力管理通过公共接口提供，不绑定默认导航或特定页面。

价值来自找到合适能力并得到完整结果。目录规模是覆盖范围，不是运行质量或任务成功率。能力详情用示例结果、输入要求和当前设备可用状态说明价值。

## 2. 已核对的本地基础与缺口

| 现有基础 | 复用方式 | 当前缺口 |
| --- | --- | --- |
| services/product/kernel.py | 延续授权、回执、任务归属与持久状态 | submit_turn 的能力集合和动作分派是固定类型，不能直接承载任意外部工具 |
| services/product/tool_library.py | 保留个人 SQL 工具、版本与验证记录 | 这是受限 SELECT 工具库，不是通用插件运行时；不要直接扩成任意脚本执行器 |
| apps/desktop/product/runtime/resources.mjs | 扩展按资源访问的产品接口 | 现有 tools/tool/manageTool 面向内置工具，需新增能力目录与状态投影 |
| apps/desktop/product/providers/deepseek.mjs | 复用模型调用、上下文打包与串行调度 | 当前提示词和动作契约固定；需要可发现工具与按需加载的 Skill 桥 |
| apps/desktop/product/providers/coding.mjs、claude.mjs | 保留独立执行器适配 | 当前连接器隔离配置，禁用或不继承插件/MCP；不自动开放用户全局插件 |
| ADR-009 与现有界面宿主 | 复用完整界面替换、启用与恢复接口 | 其他产品的 UI 扩展不自动等价于 morrow.ui/1 |

以上表格记录设计前的缺口。CORE-021 已修改相关代码接通首期闭环，但通用能力商店和所有专属插件适配仍未完成。

## 3. 适配原则

优先兼容已有标准和成熟运行时。Morrow 增加统一目录及执行适配，不要求每个上游插件改写成自有格式。

| 来源 | 首期处理 | 必须单独识别的条件 |
| --- | --- | --- |
| Agent Skills | 导入元数据、按需加载 SKILL.md 和资源 | 指定工具、脚本、依赖和运行环境必须实际存在；说明文字不授予权限 |
| MCP | 复用官方 SDK 发现和调用工具，先覆盖工具路径 | 本地进程/远程服务、认证、协议版本与输出类型；不宣称首期支持全部 MCP 特性 |
| Codex / Claude 插件包 | 解析清单，保留上游身份，将兼容的 Skills/MCP 映射到目录 | 必需的 hooks、agents、宿主私有 API 缺失时，相关能力不可标成可用 |
| 宿主专用插件 | 后续通过对应官方运行时执行，或实现明确适配器 | 运行环境、工具别名和配置语义不能仅靠改名假装等价 |
| 自定义 UI | 独立遵循现有 Morrow 前端包与 SDK | 其他产品的主题、工具卡片、桌面功能不能自动替换完整前端 |

允许导入插件的独立可用组件，但必须显示部分支持及缺失项；如果缺失组件是其必需依赖，整个相关能力不可启用。工具、协议、Windows 环境与模型表现分别验证。

官方资料：
- [Agent Skills 规范](https://agentskills.io/specification)：SKILL.md、资源目录、兼容性信息与按需加载。
- [MCP TypeScript SDK 客户端](https://ts.sdk.modelcontextprotocol.io/client)：已有连接、发现与调用工具接口；实现时重新核验版本并锁定，不以 v1 页面推断当前应选择的主版本。
- [Claude 插件清单](https://code.claude.com/docs/en/plugins-reference)：Skills、MCP、hooks、agents 等组件需分别处理。
- [OpenAI 插件打包](https://developers.openai.com/plugins/build/plugins)：可移植清单与兼容布局。
- [Codex App Server](https://learn.chatgpt.com/docs/app-server)：插件安装、列表等接口仍标开发中；不把这些接口作为当前生产依赖。

## 4. 面向用户的流程

1. 用户在聊天中说“我想整理每周资料”，或进入“添加能力”。
2. AI 从目录提出少量相关选择，说明每项能带来什么结果；用户也可直接搜索、选择。
3. 确认添加时展示必要输入、登录/费用与数据访问范围。已授予范围内的日常操作不反复询问；新的范围和外部写入按用户策略处理。
4. 系统准备依赖、连接和验证。没有准备好的项目显示具体原因，不能只因为安装包存在就显示“可用”。
5. 后续用户正常描述需求，AI 从已启用且可用的能力中选择；结果回到同一对话与任务记录。
6. 用户可单独停用、替换某个能力，或把一组搭配保存为个人组合。组合是可拆开的起点，不是固定工作流或模板限制。

能力卡只突出名称、一句用途、一幅真实示例和当前状态。来源、版本、授权说明等放详情，保留必要署名与查阅入口。

“AI 生成适配器”可以作为后续开发辅助：读取清单、生成映射和配置、提出缺失依赖、制作候选代码。候选仍需构建和行为验证；生成了文件不能直接成为已启用能力，更不能直接放进可信宿主执行。

## 5. 统一目录与调用边界

以下为拟议契约，尚未冻结或实现。

目录记录至少包括：稳定 ID、上游与作者、版本/内容标识、用途、输入输出结构、适配器类型、依赖、平台要求、所需权限、凭据引用、费用来源、兼容状态和验证记录。

源文件尽量保持原样，适配映射单独保存。凭据引用只保存标识，不包含密钥。未知许可先标记待核对，不自动纳入可分发目录。

安装、配置和验证分别记录；由这些事实推导“可以使用 / 需要连接 / 不支持当前环境 / 已停用 / 故障”等用户状态。验证绑定具体版本、适配器、系统环境与测试范围，不将一次成功承诺为永久可靠。

每次调用绑定 capability_id、插件版本、tool_id、task/turn/attempt、调用 ID、参数以及宿主授权引用。输入由 Schema 校验，结果进入现有任务回执；模型的文本总结不代替真实完成状态。工具返回的说明不能改写宿主权限。

外部调用不能跨网络与本地 SQLite 获得通用原子事务。采用先记录调用意图、再执行、再保存结果的模式；中断后可能为 outcome_unknown。外部副作用使用上游可验证的幂等机制或人工核对，不盲目重放。取消与实际停止分别记录。

本地 MCP 进程由适配器持有生命周期、限定环境和明确工作目录，不能把 Node 子进程隔离说成敌对代码沙箱。首批先用已核验依赖和明确用途；任意第三方代码执行需要独立的运行隔离工作。

不一次性把全部插件正文塞进提示词。先按设备、授权、配置和启用状态筛出可用集合，再按用途提供少量元数据；模型选择后加载相关说明和工具 Schema。必要时提供目录搜索，避免筛选永久隐藏真正需要的工具。

组合搭配默认不产生并发模型请求；继续复用产品串行执行槽、停止与恢复机制。MCP 服务提出的模型采样请求也不能绕过统一模型调用边界。

## 6. 模块拆分

| 模块 | 输入与输出 | 接口关系 | 验收重点 |
| --- | --- | --- | --- |
| 目录与清单导入 | 上游清单/Skill → 规范化能力条目、兼容诊断 | 只读导入；供发现与安装使用 | 相同名称不冲突；不运行安装脚本；必需组件缺失不误报成功 |
| 依赖与连接管理 | 条目、用户配置 → 版本化安装记录与连接状态 | 独立凭据引用；可启用、停用和更换版本 | 升级失败保留旧版本；不继承全局账号；不删除私人数据 |
| MCP 执行适配 | 已授权调用 → 实际结果、错误或结果未知 | 官方 SDK + 现有任务生命周期 | 真进程/本地服务验证；超时、取消、崩溃和重复调用有真实状态 |
| Skill 与模型发现 | 用户需求、可用集合 → 按需说明和候选工具 | 共用现有模型接口，不构建第二套主控 | 未安装能力不可假用；选择和多工具组合与结果关联 |
| 用户入口与分享 | 能力投影 → 添加、选择、搭配、停用 | 默认和替换 UI 使用同一 SDK | 换 UI 保留状态；不新增永久工具栏；分享排除账号与私人内容 |
| 跨 Agent 专属适配 | 宿主专用组件 → 委派或明确不支持 | 保持执行器可替换 | 官方运行时完成真实回执；不能以文字转换替代语义兼容 |

MCP 网络与子进程由现有 Node 宿主侧管理；Python 内核继续拥有业务状态与授权。实施前冻结外部调用的持久化边界及新增 schema，不在 Python 数据库事务内等待外部服务。

## 7. 开发顺序

### CAP-01：只读兼容与目录基础
导入标准 Skill、MCP 配置及两种插件清单的明确子集，建立版本化目录和依赖诊断。先用合成夹具及已核验源文件离线验证，不安装或执行作者代码。输出支持矩阵与逐组件诊断。

### CAP-02：一个真实 MCP 闭环
复用官方 SDK，接一个只读工具服务，走发现、授权、调用、任务回执和 UI 结果。验证鉴权缺失、工具变更、关闭、超时、取消、重复请求及崩溃；协议测试与模型语义测试分别记账。

### CAP-03：模型选择与 Skill 组合
连接按需发现及 Skill 加载，逐步增加已验证的能力。用串行 DeepSeek 在虚构材料上验证用户自然语言选择、信息不足、工具故障和组合流程。增加能力不能使原有聊天、记忆与 CSV 流程回归。

### CAP-04：简洁入口与能力搭配
实现“添加能力”、个人搭配、停用与版本恢复。共享搭配导出能力引用、兼容要求和明确允许分享的设置；默认排除记忆、对话、凭据、私人目录与私有服务地址。导入他人的组合只创建待配置状态，不自动执行。

### CAP-05：跨运行时与 AI 辅助适配
按真实需求扩展宿主专属组件、隔离运行与适配器候选生成。已有稳定协议覆盖不了的部分逐一验证，不追求一次兼容所有 Agent。

先形成 6–10 项可验证能力的首批目标，组合成 2–3 条完整使用体验；不是当前已完成数量，也不按工具 API 数量堆指标。候选方向：资料与表格、内容制作、日常安排。现有 CSV、文本成果、提醒可以作为起点；PDF、演示文稿、日历等外部能力在真实接通前只列为候选。

## 8. 发布与产品表达

宣传基于已验证的实际结果。上游开源项目提供基础实现，Morrow 提供发现、准备、搭配、连续状态与统一体验；来源可查、保留作者贡献与许可要求。

官网保持已确定的克制设计：一个“添加你需要的能力”段落配少量真实示例，完整目录进入独立页面。主界面和首屏不随着兼容数量增长而变成工具图标墙。

该路线可在现有邀请试用反馈中逐步验证，不将全面插件市场建设变成首轮用户试用的前提。现有安装包仍不能宣传成已具备上述跨生态适配。
